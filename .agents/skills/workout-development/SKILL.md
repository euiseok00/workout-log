# Workout Log 개발 오케스트레이터

## 목표와 완료 기준

현재 요청에 필요한 기능만 React 프론트엔드와 Spring Boot 백엔드에 구현하고, 관련 PostgreSQL 영속화와 Spring Security 경계를 함께 검증한다.

완료하려면 다음 조건을 만족해야 한다.

- 요청한 사용자 동작과 오류 동작이 구현되어 있다.
- 변경된 HTTP 생산자와 소비자의 경로, 메서드, 상태 코드, JSON 필드, null 및 오류 형식이 일치한다.
- 데이터 변경은 현재 기능에 필요한 엔티티, 관계, 제약, 마이그레이션 범위만 구체화한다.
- 관련 린트, 테스트와 빌드가 통과하거나, 실행할 수 없는 검사가 `not_run`과 사유로 보고된다.
- 리뷰에서 발견된 필수 결함이 해결되고 영향받는 경계가 재검증된다.

README의 MVP와 Core Domain은 방향을 제시하는 초기 설계다. 구현되지 않은 API, 테이블, 관계를 미리 확정하지 않는다.

## 기본 구조와 명령

- 프론트엔드: `frontend/`, React + Vite + JavaScript + ESLint
- 백엔드: `backend/`, Java 21 + Spring Boot + Gradle
- 프론트 검증: `npm run lint`, `npm run build` (`frontend/`에서 실행)
- 백엔드 검증: 환경변수 설정 없이 `./gradlew test` (`backend/`에서 실행, Windows PowerShell에서는 `.\gradlew.bat test`)

실제 스크립트와 Gradle 구성을 먼저 읽는다. 위 명령이 프로젝트 변경으로 달라졌다면 현재 파일의 명령을 사용한다.

## 백엔드 PostgreSQL 통합 테스트 정책

- PostgreSQL 통합 테스트는 기존 `PostgresIntegrationTest`를 상속하고 Testcontainers + `@ServiceConnection` 구성을 재사용한다.
- `./gradlew test`가 PostgreSQL 컨테이너를 자동 생성하고, 빈 컨테이너 DB에 Flyway `V1`부터 최신 migration까지 적용하며, 테스트 종료 후 컨테이너를 제거하는 현재 수명 주기를 유지한다.
- 로컬 `workout_log_test` 데이터베이스나 `localhost:5432`의 별도 테스트 DB를 사용하지 않는다. 개발 DB `workout_log`는 테스트에서 절대 수정하지 않는다.
- 테스트를 위해 `WORKOUT_DB_PASSWORD` 또는 `WORKOUT_JWT_SECRET`을 요구하거나 `SPRING_DATASOURCE_URL`을 로컬 DB 주소로 설정하지 않는다. JWT secret은 `test` profile의 테스트 전용 값만 사용한다.
- 테스트용 PostgreSQL을 별도의 임시 `docker run` 명령으로 직접 실행하지 않는다. 정상적인 백엔드 전체 테스트는 추가 환경변수 없이 `backend/`에서 `./gradlew test`만으로 동작해야 한다.

## 역할과 최소 실행 방식

메인 세션이 요구사항 해석, 작업 장부, 공용 계약, 공유 설정, 통합과 완료 판정을 맡는다.

- `workout_worker`: 메인이 지정한 파일만 구현한다.
- `workout_reviewer`: 완료된 변경을 읽기 전용으로 검토한다.
- `workout_qa`: 제품 코드를 수정하지 않고 명령 실행과 경계면 검증을 맡는다.

기본은 메인 중심의 순차 실행이다. 하나의 작은 변경은 메인이 직접 구현하고 검증할 수 있다. 작업이 명확히 독립적이거나 전문적인 독립 검증이 구현 위험을 실질적으로 줄일 때만 worker, reviewer 또는 QA를 선택적으로 호출한다. 동시 실행은 독립된 파일 소유권과 충돌하지 않는 빌드 출력이 있을 때 최대 2개 스레드로 제한한다.

하네스 실행 장부가 필요한 큰 작업은 `.agents/skills/harness/references/runtime-guide.md`를 읽고 `run.py init` 또는 `resume`을 사용한다. 짧은 단일 파일 변경에는 실행 기록을 의무화하지 않는다.

## 실행 절차

1. `README.md`, 현재 소스, 테스트, 설정과 `git diff`를 읽고 실제 상태를 확인한다.
2. 요청을 사용자 동작 단위로 자르고, 각 단위의 입력, 출력, 실패 조건, 영향받는 파일과 검증 명령을 정한다.
3. 이번 작업에서 확정해야 하는 계약만 짧게 기록한다. API라면 메서드·경로·인증·요청·응답·오류를, DB라면 컬럼·제약·관계·마이그레이션·롤백 영향을 포함한다.
4. 같은 계약을 쓰는 프론트엔드와 백엔드를 함께 추적한다. 한쪽만 존재하면 실제 통합 검사를 `not_run`으로 남기고 후속 조건을 적는다.
5. Spring Security 변경은 인증 주체, 공개/보호 경로, 소유권 검사와 오류 응답을 확인한다. 비밀값은 저장소에 넣지 않는다.
6. JPA 변경은 엔티티만 고치지 말고 저장·조회 코드, 직렬화 경계, PostgreSQL 제약과 기존 데이터 영향을 확인한다. 마이그레이션 도구가 아직 없다면 임시 자동 스키마 변경을 가정하지 말고 해당 기능에서 도입 여부를 결정한다.
7. 최소 구현 후 가장 가까운 관련 테스트부터 실행한다. 관련 테스트가 통과하면 완료 직전에 전체 테스트를 1회 실행한다. 전체 테스트가 실패하면 실패한 영향 범위만 수정·재검증한 뒤 최종 상태에서 전체 테스트를 다시 실행한다. 자동 테스트로 확인된 동작은 테스트 공백이나 별도의 환경 증명이 필요한 경우가 아니면 수동 API·DB 검증으로 반복하지 않는다.
8. 리뷰는 요구사항과 diff를 기준으로 기능, 계약, 보안, 데이터 무결성, 회귀 위험을 확인한다. 결함 수정은 워커 또는 메인이 하고 QA가 영향 범위를 다시 검증한다. 수정·재검증은 기본 최대 2회다.
9. 최종 결과에 변경 파일, 확정한 계약, 실행한 검사와 상태, 실행하지 못한 검사, 남은 후속 작업을 보고한다.

## 프론트엔드-백엔드 계약 점검

타입 선언이나 문서만으로 일치를 판단하지 않는다. 실제 Spring 컨트롤러·DTO·예외 처리와 React 요청·응답 소비 코드를 함께 비교한다.

- 기본 URL과 `/api` 접두사, HTTP 메서드, 경로 및 쿼리 파라미터
- 인증 방식, 자격 증명 전달, 401과 403 처리
- 요청 `Content-Type`, 필수·선택 필드와 Validation 오류
- 응답 래핑, 이름 표기, ID와 날짜 표현, 빈 목록과 null 처리
- 생성·수정·삭제의 상태 코드와 프론트 상태 갱신

공용 계약 파일이나 OpenAPI는 반복되는 불일치가 생기거나 실제 소비자가 둘 이상일 때 도입한다. 현재 기능 하나를 위해 전체 MVP 계약을 선행 설계하지 않는다.

## 데이터베이스 변경 기준

스키마 변경이 필요한 작업에서만 구체화한다.

1. 현재 엔티티와 저장소 쿼리, 실제 PostgreSQL 설정을 확인한다.
2. 새 컬럼과 관계의 nullability, 기본값, 유일성, 인덱스, 삭제 동작을 결정한다.
3. 기존 데이터가 있으면 backfill과 호환 순서를 정한다.
4. 선택된 마이그레이션 도구의 버전 파일을 추가하고 테스트 환경에서 적용을 확인한다.
5. 엔티티, 쿼리, API 직렬화와 프론트 소비를 함께 재검증한다.

마이그레이션 도구나 운영 데이터 정책이 아직 정해지지 않았다면, 첫 실제 스키마 변경 작업에서 선택 근거와 배포 순서를 확정한다.

## 리뷰 및 QA 결과 형식

검사는 `passed`, `failed`, `not_run`으로 기록한다. `not_run`은 생략 이유를 포함하며 성공으로 계산하지 않는다. 리뷰 결함은 심각도, 파일과 근거, 사용자 영향, 재현 또는 실패 조건, 권장 수정 범위를 포함한다.

필수 테스트 실패, 미해결 보안·데이터 무결성 결함, 생산자와 소비자의 확정 계약 불일치는 완료를 막는다.

## 부분 재실행

후속 요청에서는 변경된 입력과 계약부터 영향 범위를 추적한다. API 계약이 바뀌면 백엔드 생산자와 프론트 소비자 및 관련 테스트를, DB 계약이 바뀌면 마이그레이션·JPA·API·소비자를 다시 검증한다. 관련 없는 이전 결과와 사용자 변경은 보존한다.

## 테스트 시나리오

- 정상: 독립된 프론트와 백엔드 구현이 같은 계약에 맞고, 통합 후 린트·테스트·빌드가 통과한다.
- 오류: 응답 필드나 인증 규칙 불일치를 QA가 발견하면 구현 소유자가 수정하고 관련 경계를 재검증한다.
- 후속: API 또는 스키마 일부가 바뀌면 영향받는 생산자, 소비자와 테스트만 다시 실행하고 이전 기록을 보존한다.
